# Foundation Constitution v0.1

## 目标

建设一个基于关系数据库、面向对象和对象关系的通用数据底座。平台应能保存对象当前状态、对象关系、状态历史、数据来源和变更事件，并向上层领域业务提供统一的查询、写入、授权和审计能力。

## 核心原则

1. **领域中立**：底座不理解标签、风险等级、廉洁提醒等具体业务含义。业务语义通过 Domain Pack 提供。
2. **对象和关系同等重要**：关系是有稳定身份、属性、生命周期和历史的实体，不能退化为对象表中的外键字段。
3. **当前与历史分离**：当前状态用于高频查询，历史事实不可覆盖；任何状态变化都必须可追溯。
4. **业务写入受控**：生产写入必须经由 Action 或受控同步流程，禁止通过通用 CRUD 绕过校验、授权和审计。
5. **数据库可替换**：核心引擎只依赖 Storage SPI；数据库差异封装在 Provider 和 Dialect 中。
6. **安全默认拒绝**：缺失租户、主体、权限或必要策略时拒绝操作，不能以开发模式行为代替生产安全。
7. **事务一致性优先**：对象、关系、历史、审计和 Outbox 记录必须在同一事务中保持一致。
8. **来源可追溯**：同步或计算产生的数据必须记录来源系统、来源记录、采集时间和变更依据。
9. **可验证契约**：每个核心语义都要有接口契约和一致性测试，而不是只依赖文档描述。
10. **渐进式复杂度**：首期采用模块化单体和关系数据库；只有在负载或隔离要求明确时才拆分服务或引入图投影。

## Foundation 范围

Foundation 必须覆盖：

- Domain Pack 和 Schema 编译；
- 对象、关系、状态和历史；
- Action、事务、并发控制和幂等；
- Storage SPI 与关系数据库 Provider；
- 租户、认证、授权、字段脱敏；
- 事件、Outbox、审计和数据血缘；
- 外部数据同步、来源和冲突处理；
- GraphQL、REST 和内部 SPI 契约。

Foundation 不实现：

- 标签赋值规则和标签业务生命周期；
- 风险识别模型；
- 具体提醒内容匹配和推送策略；
- 具体外部渠道业务流程；
- 具体单位或人员主数据的权威维护。

## 实现约束

- 首选 Java 21 LTS；必须保持对项目批准的国产操作系统和数据库环境的可部署性。
- 核心 SQL 不得依赖 Apache AGE、PostgreSQL JSONB 或厂商专有函数；这些能力只能作为 Provider 的可选增强。
- 所有数据库 Provider 必须通过同一套 SPI 一致性测试。
- 规约变化必须通过 ADR 记录原因、影响和迁移方案。
