# 时间历史格式2：升级与旧数据边界

本次修复普通更新回溯覆盖、删除事实失效后复活及列表忽略时间参数的问题。规范见ADR-0005。

## 数据布局变化

of_object_history、of_link_history各增加`temporal_format INTEGER NOT NULL DEFAULT 1`。已有表通过元数据检测后增列；已有行得到1，新代码写历史时显式写2。

- 格式1：旧实现的valid_from/valid_to不具备本版转换语义，不能假设直接套新查询算法即可正确。
- 格式2：从本次有效时间起的完整状态断言；普通创建/更新以及删除均追加，删除以DELETED表示持续终止；记录时间和版本决定同一业务时点的最新已知断言。

不修改旧行的valid_from、valid_to、recorded_at、snapshot、version或业务属性，不把升级时刻当作历史生效时间。

## 升级后的行为

- 当前对象/关系读写、按版本读取和原始历史审计继续可用。
- 普通新写入追加格式2，即使该实体此前存在格式1；不会重写旧事实。
- 时间单查、时间列表或历史遍历涉及格式1时抛出`TemporalHistoryUnavailableException`，错误码`TEMPORAL_HISTORY_MIGRATION_REQUIRED`。
- 新对象或新关系完全由格式2构成时可正常时间查询；混合格式实体不能仅忽略格式1再回答，以免伪造过去。
- 显式effectiveAt补录涉及旧实体历史/旧端点或需检查的旧关系时间线时拒绝；默认当前时间的普通写入不因此停摆。
- JDBC时间列表按相关类型加载已知历史；历史遍历按涉及的对象/关系类型加载，因此可能因同类型旧数据拒绝整次查询。这是当前保守边界，尚未完成按可达记录优化。

## 真实数据迁移要求

实际升级前备份并确认运行库/驱动可执行增列。若确需恢复旧实体的时间查询，须按业务来源明确每个版本的生效时点，验证对象/关系、删除、补录、记录时间和历史基数；形成独立迁移方案、可恢复备份及验收证据。不能批量把temporal_format改为2，也不能只把全部有效时间替换为recorded_at。

若历史确实只有“按记录版本变化”的依据，可以另行定义经确认的降级查询口径；本版本没有自动启用这一推断。本次没有提供或执行旧业务时间回填脚本。

## 验证范围

H2升级测试模拟没有temporal_format的旧表，验证重复初始化、旧行完全不变、当前更新/解除/重建关系可用、新实体时间查询可用、旧实体时间查询明确失败。另一测试重建Provider，验证格式2的迟到更新和删除历史仍可正确查询。真实国产库迁移须在目标环境单独验收。
