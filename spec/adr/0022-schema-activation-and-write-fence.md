# ADR-0022：模型激活、存量校验与事务提交门禁

日期：2026-09-28。状态：JDBC存储激活和写入门禁已实现；读请求/应用装配版本绑定仍待完成。

## 已登记与已激活分离

ADR-0021的注册表只保存候选模型，不代表模型已用于存储。本阶段增加数据库级激活状态：

- JDBC存储使用registry_key=storage的模型注册表；默认注册表default仍独立。
- `of_active_schema`保存当前schema_version、SchemaFingerprint和唯一activation_id。
- `of_schema_activations`追加每次激活的前后版本、指纹、时间、调用主体/请求租户及MigrationPlan说明。

登记新候选不会改变active指针，也不会阻止当前有效部署写入。激活可以选用已经登记且内容相同的最新候选，避免重复登记；激活审批按当前已激活模型到目标模型的差异单独检查，不能借一个相对后续候选为SAFE的登记绕过实际BREAKING切换。

## 启动与显式切换

JdbcStorageProvider的普通`applySchema(context, schema)`现在仅用于：

1. 首次初始化：校验现存当前数据，登记并激活模型。
2. 同一模型重新连接：验证激活记录与注册表快照，绑定当前激活版本，不新增登记或激活记录。

如果已激活模型与配置不同，即使是SAFE变更，普通启动也拒绝漂移，不允许旧部署因启动而改回自己的模型。模型变化明确调用：

```java
SchemaVersion activated = storage.activateSchema(context, nextSchema,
        reviewedPlan, expectedActiveVersion);
```

expectedActiveVersion绑定审查时的激活版本；竞争者只有一个成功，过期预期版本拒绝。`boundSchemaVersion()`返回本Provider实例绑定的版本，未绑定为0，不代表数据库最新版本。BREAKING切换仍要求MigrationPlan.approved；该API是可信部署操作，不是公开业务HTTP接口。

模型注册追加、激活日志和active指针在同一JDBC事务提交。已有候选不重复追加；失败不会更新Provider的内存绑定。重新激活曾使用的模型会得到新的登记版本/activation_id，旧进程不能因指纹相同而重新获得写入资格。

对象基础表、历史格式列及注册表/激活表的初始DDL独立初始化，不宣称跨所有数据库的DDL可回滚。每个Provider只初始化基础表一次；运行中的模型切换不会重复执行基础DDL。

## 存量事实校验

首次采用或切换到不同模型时，在激活事务中校验所有租户的已提交当前事实：

- 活跃对象的类型、已知属性、必填、类型、枚举及字段/类型CEL约束。
- 按租户、对象/关系类型和字段检查唯一性，不将不同租户的相同值视为冲突。
- 活跃关系的类型、属性、端点类型与存在性，以及ONE_TO_ONE/ONE_TO_MANY/MANY_TO_ONE基数。
- 字面默认值和readonly生成器不用于回填已有事实，不修改对象版本或历史。

软删除对象和已结束关系作为历史保留，不要求它们满足新模型的当前状态约束。已有活跃关系可以引用软删除但仍存在的对象，沿用原存储生命周期规则；不把这种既有情况误判为物理缺失端点。重新恢复已结束关系时，内存/JDBC都会检查其原端点是否仍符合当前声明，禁止旧关系在改变端点定义后被错误恢复。

批准标志不能替代数据修复。可以使用正常变更实现“先加可选字段→回填→批准收紧为必填”的迁移。自动类型转换、删除存量属性、任意SQL迁移脚本和大批量回填执行器仍未实现；候选模型不能用于解释尚不合规的事实。

同一模型重新连接不重复全库扫描。已有原始SQL/旧版本造成的数据问题仍由修复或漂移检查处理，不能据此声称每次启动都完成了完整数据审计。

## 事务门禁及并发

每个JDBC事务捕获不可变的模型绑定（版本、指纹、activation_id），字段/关系校验使用该事务捕获的模型，避免同一Provider热切换时混用两份模型。

变更前检查持久激活身份；获得租户写锁后再次检查。提交时对active行短暂FOR UPDATE，再核对身份，持锁至物理提交。任何不一致都会标记事务必须回滚并抛SchemaVersionMismatchException，不能捕获后继续提交。

这不是全事务持有全库写锁：不同租户的未提交变更可以并行。激活取得active行锁后冻结所有受管事务的提交，并在READ_COMMITTED下校验当前已提交集合；校验期间未提交的新旧变更不会进入该集合。激活成功后，已执行但尚未提交的旧模型事务在提交门禁失败并整体回滚。若一个业务事务已先取得提交门禁，它先完成提交，激活随后看到其已提交事实。

激活路径按active→registry加锁，不获取租户写锁；业务事务持租户写锁，提交时获取active锁。激活读取事实不使用FOR UPDATE，避免与在途业务写入形成锁环。新版本事务正常使用原租户约束串行化，提交门禁只在短提交窗口串行化。

所有事务写入口，包括对象/关系、命令回执、持久Action执行、审计和outbox均受门禁约束，空事务提交也会检查。模型切换不会自动更改已构造的应用对象。JDK HTTP适配器将旧模型写入映射为409 / SCHEMA_VERSION_MISMATCH / retryable=false，宿主重新装配当前部署后才可继续，同一业务幂等键的失败尝试不产生虚假完成回执。

## 边界与后续工作

本阶段的持久门禁针对JDBC写入。**当前公共读SPI及已构造ApplicationService尚未绑定activation_id**，不能声称旧应用的字段投影、动作清单或FGA资产已经实现完整热切换治理。部署切换需要重新构造匹配模型的应用层；读请求/应用装配绑定和一致读快照是下一重点。

内存Provider继续使用原有进程内revision/schema事务冲突机制，未伪装成持久激活协议。Schema激活跟踪OntologySchema，不涵盖独立Action manifest、字段策略或权限模型资产的整个发布生命周期。

门禁仅约束遵循该协议的新JDBC Provider。旧构建或原始SQL写入不会自动获取提交门禁；升级到此协议前必须停止这些写入，再执行首次采用校验。没有修改正在运行的Mirror JAR或业务数据库，也没有对真实生产数据执行采用或回填。

H2验证了MVCC读取、行锁和恢复行为。真实PostgreSQL/国产库、性能、DDL/物理模式漂移、完整迁移执行与运维仍需独立验收。激活日志保存调用时的治理信息，不将其称为外部签名或完整审批工作流。
